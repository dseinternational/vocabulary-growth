# Parameter recovery

> [!NOTE]
> Drafted by an LLM-based AI tool (Claude Code/Opus 5).

A parameter-recovery study regenerates a dataset from a model at a known parameter draw, refits the model to that dataset, and asks whether the truth is found again. It answers a question the posterior-predictive calibration written by every fit cannot: **if this model were true, could this sampler identify its parameters from data of this size, shape and missingness?** A quantity whose truth sits far outside its recovered posterior points to a parameter that is not identified, a constraint that is mis-specified, or a chain that has not converged — each of which makes the published interval for that quantity untrustworthy.

This closes half of the second outstanding acceptance item in [#163](https://github.com/dseinternational/vocabulary-growth/issues/163) ("quantitative posterior-predictive calibration plus simulation/parameter-recovery checks for the preferred models"). The calibration half is already automatic: every fit writes `posterior_predictive_calibration.csv`.

## What the harness guarantees

The value of a recovery check rests entirely on the synthetic data being generated by *the same model* that is then fitted to it. Three properties enforce that, and each is covered by a test that runs in CI:

- **The data come from the model's own likelihood nodes.** The engine's build code constructs the model, and `pymc.sample_posterior_predictive` draws the observed nodes at one fixed parameter draw. No mean function, dispersion function or row denominator is restated in the harness, so a change to a model cannot leave a stale copy behind in the simulator.
- **The nesting is coherent.** Words spoken and words signed are modelled conditionally on the child's comprehension total, and that denominator is fixed at build time. Comprehension is therefore drawn first, written into the analysis frame, and the model is **rebuilt** so the engine re-derives every denominator from the *simulated* parent. After the last round, the denominators and nested/marginal flags of a model rebuilt from the finished frame are compared against the ones the simulation used; a mismatch aborts the run.
- **The design and the missingness are real.** Only outcome counts are replaced. Ages, studies, children, and the pattern of which outcomes each row reports are the study's own, so the check is about recovering parameters from data like ours, not from a convenient idealisation.

One consequence is worth stating plainly. In the real data a handful of rows record a spoken count larger than the recorded comprehension count, and the pipeline routes those to the marginal likelihood as source-data violations. The model has no mechanism to produce such a row, so the synthetic data contain none, and those rows are nested in the synthetic dataset. That is correct — the data are generated by the model as specified — but it means the recovery check does not exercise the violation path.

## Running a study

```bash
python scripts/fit_recovery.py headline --config test
```

`headline` is VG10, VG12 and VG15 — the three models #163 gates. Use a single model key for one model, or `all` for every supported model. Each replicate simulates, refits and scores.

Useful options:

| Option | Effect |
| --- | --- |
| `--replicates N` | Replicates per model (default 3). |
| `--replicate N` | Run only replicate N; repeatable. |
| `--truth posterior\|prior` | Where the truth comes from (default `posterior`). |
| `--config` | Sampling configuration; `test` is the honest tier for a recovery claim. |
| `--simulate-only` | Simulate and stop. No MCMC, so this is seconds per replicate. |
| `--fit-only` | Refit existing simulated data. |
| `--compare-only` | Re-score existing recovery fits. |
| `--output-dir` | Output root, as elsewhere in the project. |

The stages are separable so a long run can be resumed, and so the simulation can be inspected before hours of sampling are committed. A sensible sequence for a real study:

```bash
python scripts/fit_recovery.py headline --config test --simulate-only
python scripts/fit_recovery.py headline --config test --fit-only
python scripts/fit_recovery.py headline --config test --compare-only
```

Recovery fits land in `<output root>/models/<model_id>-<config_name>-recovery-rNN/` and never touch a model of record. `sync_report_figures.py` and `check_fit` key off the registered config names, so they skip these directories — a recovery fit cannot leak into the technical report.

### Choosing the truth source

`--truth posterior` (the default) takes each replicate's truth from the model of record's stored posterior, one evenly spaced draw per replicate, spread across chains so replicates are not autocorrelated near-duplicates. This asks whether the parameters are recoverable **in the regime the study actually reports**, which is the question worth answering. It requires the model of record to have been fitted at the same output root, because it reads that fit's `trace.nc`.

`--truth prior` draws each truth from the model's prior instead. It needs no fitted trace, which makes it the option for a model that has not been fitted yet and for smoke-testing the harness. It is **not** a substitute: the priors are deliberately broad, so a prior draw can put a 12-month-old with Down syndrome at several hundred words understood. Recovery at such a truth says something about the sampler over the whole prior mass, not about the estimates in the report. Prior-truth results should be labelled as such wherever they are quoted.

## Reading the result

Per model, `<output root>/comparisons/recovery/`:

- `recovery_<model>_rNN.csv` — one row per target quantity: the truth, the recovered posterior median/mean/sd, the standardised error `z`, the 50% and 89% intervals with containment flags, and `truth_quantile` (the truth's rank within the posterior draws).
- `recovery_<model>_rNN_aggregates.csv` — for the high-dimensional random effects. Individual child effects are barely identified by design, so what is reported is whether the *set* of them is recovered: interval coverage across children, and the correlation between the true effects and their posterior means.
- `recovery_matrix_<model>.csv` — one row per replicate plus a pooled row.

Target quantities are selected from the model itself by dimension, not from a hand-maintained list, so a model that gains a reported quantity gains its recovery check. Scalars, the population trajectories at the query ages, and the study effects are scored element by element. Excluded, with reasons in `recovery/compare.py`: the standardised age grids (design, not parameters), the logit-scale duplicates of probability-scale quantities (which would double-count the same information), and the non-centred `_raw` offsets (reparameterisation internals).

### The gate

A replicate is only assessed if its recovery fit's convergence is positively confirmed (`max_rhat ≤ 1.01`, `min_ess ≥ 400`, the same thresholds the sensitivity matrix uses). Otherwise the verdict is `NON-CONVERGED (not assessed)` or `UNVERIFIED (no recorded diagnostics; not assessed)`, and the replicate contributes nothing to the pooled row. A truth outside the posterior of a chain that has not mixed is sampler noise, not evidence about identifiability.

Note that the pipeline's own hard convergence gate fires only at reporting-quality configurations, so a `dev` or `test` recovery fit completes even when it under-converges. The harness's gate is what catches that, and at `dev` it usually will: two chains of 500 draws do not converge these hierarchical models.

### What a handful of replicates can and cannot show

Read `coverage_ci89` as exactly what it is: the fraction of target quantities whose 89% interval contained the truth. It is **not** a coverage estimate. The quantities within a replicate are strongly correlated and come from a single truth, so their hit rate has far less information than the count of them suggests. Simulation-based calibration — which is what would license a claim about interval coverage — needs on the order of a hundred replicates before rank uniformity means anything. The pooled row is labelled indicative for this reason.

What a small number of replicates *does* support:

- A quantity whose truth is far outside its posterior (`|z|` of 4 or more) is a real finding and worth investigating, whether it indicates a non-identified parameter or a sampling problem.
- A quantity recovered tightly and centrally across replicates is reassuring about identifiability at this data size.
- Systematic one-directional error across the query ages of a trajectory suggests a constraint or anchor is pulling the fit, which is exactly the concern the Target 8 anchor sensitivities address.

`truth_quantile` is the statistic a full calibration study accumulates. It is recorded per quantity per replicate so that a later, larger run can pool them without new code.

## Coverage and known gaps

Supported: VG07–VG13 and VG15 (the study-random-effect bivariate engine, the univariate engine, and the joint sign/speech engine). This covers all three headline models.

Not supported, deliberately:

- **VG16.** Its cross-lag predictor is built from each child's earlier-wave comprehension count, so the design matrix is a function of the outcome. Simulating every wave at once would generate the data under real-data lags and fit it under synthetic-data lags, and the resulting "recovery failure" would be an artefact of the harness. A correct VG16 check needs wave-sequential simulation.
- **VG01–VG05 and VG14.** Descriptive baselines on the non-random-effect engines, superseded for the estimands #163 gates by VG10 and VG15.

Requesting an unsupported model gives an error stating the reason.

## Cost

Simulation is seconds per replicate — it builds the model two or three times and draws one parameter set, with no MCMC. The refit costs whatever a fit of that model costs at the chosen configuration, so the run is dominated by sampling and scales as (models × replicates). Plan a `test`-tier headline study accordingly, and prefer `--simulate-only` first to confirm every coherence check passes before committing the sampling time.

## Relationship to the other robustness work

Recovery, prior sensitivity and calibration answer different questions and none substitutes for another:

- `scripts/fit_sensitivity.py` — does a *prior* choice move the reported estimate? (`docs/models/PRIORS.md`)
- `posterior_predictive_calibration.csv`, written by every fit — does the model describe the observed data?
- `scripts/fit_recovery.py` — can the sampler identify the model's own parameters from data like ours?
